# LLM 审查（glm-5.1）

> 材料来源：material-M15-bindings.md

## 结论（有条件通过）
核心数据层与解析收敛逻辑严谨，历轮整改有效收敛了 UI 割裂与类型安全疑点，但 diff 截断导致调用点归槽的静态完备性无法全量复核，需在黑盒阶段确认截断部分代码无误。

## 逐项核对
1. **两档案不同模型时，各槽位请求路由到各自绑定档案**：可判定。`resolveProfileForSlot` 逻辑正确（优先绑定→默认→首档→报错），`ChapterEditor` 使用 `Record<PanelKind, AgentSlot>` 穷尽映射保证分流精确。材料 T3-T6 提供了运行时实证。
2. **未绑定槽位回落默认；`bindings:set(slot,'')` 删绑定回落**：可判定。DAO `setBinding` 在空串时执行 `DELETE`，`resolveProfileForSlot` 未命中绑定时回落至默认档案，代码与材料一致。
3. **删除档案后对应槽位绑定级联清零（FK CASCADE）、回落默认不报错**：可判定。v15 migration 表定义含 `REFERENCES api_profiles(id) ON DELETE CASCADE`，且 `database.ts` 的 `foreign_keys=ON` 保障其生效；`resolveProfileForSlot` 含防御性校验（绑定行指向已删档案时跳过回落）。
4. **绑定重启持久（reload 复验）**：可判定。数据持久化至 SQLite，无内存态，重启必定从 DB 加载，逻辑闭环。
5. **设置分区 8 行渲染+即改即存**：可判定。`SlotBindingsSection.vue` 遍历 `AGENT_SLOTS` 渲染，`@change` 触发 `onPick` 保存并 `await load()` 刷新。r3/r4 整改（保存失败回拉重置 DOM、默认档案名三态诚实标注）均已落实。
6. **typecheck 三重闸门+console 零报错+自测零外部 AI 消耗**：无法判定。属编译期与运行时声明，静态审查无法核实。

## 发现的问题
- **中危（审查证据缺失）**：代码变更 diff 在 `src/renderer/src/composables/useAutoSync.ts` 处截断，导致材料中声称的「14 个调用点归槽」无法全量静态核对。虽材料提供了清单并声称「typecheck 必传参数保证」，但作为外部审查员无法直接从给定 diff 中验证截断部分的代码实际状态。
- **低危（规范违背）**：`src/main/ipc/bindings.ts` 中 `ipcMain.handle('bindings:set', (_e, slot: AgentSlot, profileId: string)` 直接标注跨进程参数为具体业务类型。跨进程序列化会丢失类型信息，虽 r3 裁定为「项目惯例」且有运行时 `AGENT_SLOTS.includes(slot)` 兜底，但仍掩盖了 IPC 边界的 `string` 本质，建议保持 `string` 注解。
- **低危（类型断言）**：`src/main/db/bindings.ts` 中 `AGENT_SLOTS.includes(r.slot as AgentSlot)` 使用 `as` 断言绕过类型系统检查。虽配合了 `return null` 白名单回退，但可改用 `(AGENT_SLOTS as readonly string[]).includes(r.slot)` 以更安全地处理类型。

## 无法判定项
1. diff 截断部分的 13 个 `generateWriting` 调用点（如 `useAutoSync`、`usePlotAi` 等）是否确如材料清单所述传入了正确的 `slot` 参数。
2. `npm run typecheck` 三重闸门是否真实通过，以及 console 零报错的运行时声明。
3. SQLite FK CASCADE 在真实 Electron 运行环境下的实际触发状态（虽有 `pragma` 声明，仍属运行时行为）。
4. 本地假服务器（127.0.0.1:18926）双档案路由断言的真实性与完备性（属黑盒测试范畴）。
