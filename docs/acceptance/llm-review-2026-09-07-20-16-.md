## 发现的问题

### 1. 材料疑点：全局 grep 证据缺失上下文（严重级别：中）
材料中「全仓旧命名 grep 实证」部分仅输出了 `0`，缺乏命令行本身（如 `grep -rn "墨灵" src/`）及路径回显。在 diff 被截断的前提下，该证据不足以支撑「全局零残留」的结论。

### 2. 规范违背：v11 数据迁移中冗余的嵌套事务定义（严重级别：低）
在 `src/main/db/database.ts` 的 v11 `migrate` 函数内：
```typescript
const retag = db.transaction((table: string) => { ... })
// ...
retag('plot_events')
retag('scenes')
```
而该 `migrate` 函数本身已经被外层的 `const run = d.transaction(() => { d.exec(m.sql); m.migrate?.(d); ... })` 包裹。在 better-sqlite3 中，嵌套调用 `db.transaction` 虽然会创建 SAVEPOINT 且能正常工作，但此处 `retag` 仅在 `migrate` 内部调用两次，将其定义为事务函数属于过度设计。应直接将其改为普通辅助函数 `const retag = (table: string) => {...}`，由外层统一的事务保证原子性，避免嵌套事务带来的语义混淆与轻微性能开销。

### 3. 逻辑优化：白名单守卫的静态防御过剩（严重级别：提示）
在 v11 `migrate` 函数中引入了 `ALLOWED_TABLES` 白名单：
```typescript
const ALLOWED_TABLES = new Set(['plot_events', 'scenes'])
// ...
if (!ALLOWED_TABLES.has(table)) return
```
由于 `retag` 是私有闭包函数，且仅以硬编码的 `'plot_events'` 和 `'scenes'` 调用，此处白名单校验永远不会被触发。虽然回应了二轮审查的防御要求，但属于无意义的死代码。

## 无法判定项

1. **全局零残留**：由于 diff 被截断且 grep 证据形式过于简略，无法判定项目内是否还存在「墨灵」「创世台」「万物百科」等旧命名残留。
2. **黑盒轨道覆盖与应用后 diff 断言**：属于运行时动态验证，静态审查无法确认 M107 回归断言的实际执行结果与通过状态。
3. **v11 迁移在生产数据库上的实际执行**：迁移逻辑（SQL+JS 逐行处理）在静态层面正确，但面对历史脏数据（如极深嵌套 JSON、超大 tags 数组）时是否会引发性能瓶颈或异常，需运行验证。
