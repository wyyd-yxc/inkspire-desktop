| P1 | 一般 | **文档与实现不一致（违反项目自身规则）**：architecture.md 第 4 节写「浅色水墨风：宣纸白背景、黛青主色」，而实际 theme.css 实现并经实测生效的是「淡紫学院风」（`--color-paper:#f5f3fa` 淡紫底 + 罗兰紫主色 `#6c5ce7`，注释自称依据官方截图校准）。代码方向正确（与验收点 1 及 refs/ 截图一致），错在设计文档未随实现更新——design-goals 第 4.2 条明确「文档与代码不一致视为 bug」，architecture.md 卷首也要求「架构变更必须先改本文件再改代码」 | docs/design/architecture.md 第 4 节 ↔ src/renderer/src/styles/theme.css |
| P2 | 一般 | **IPC 样板偏离自家规范**：coding-standards 第 7 节要求「主进程所有 IPC handler 必须 try/catch，错误以 `{ ok: false, error }` 结构返回」。当前唯一的 handler `app:ping` 无 try/catch、返回裸字符串 'pong'；`src/shared/ipc.ts` 定义的 `IpcResult<T>` 零引用。M0 的 ping 几乎不可能抛错、无实际风险，但它是仓库里第一个 handler，后续里程碑容易照此样板复制，契约类型形同虚设 | src/main/index.ts:38、src/shared/ipc.ts |
| P3 | 一般 | **worklog 会话记录缺失**：worklog 仅有会话 1（立项），其「下一步」所列的脚手架搭建、refs/ 下载、首次 commit 均已发生在 commit 8f3a51a 中，但无对应会话记录——违反 documentation-standards 第 3 节「每次开发会话结束时必须追加一节」。连带：coding-standards 第 8 节要求新增依赖（pinia/vue-router/tailwindcss/electron-vite 等）在 worklog 登记包名、用途、备选方案，亦未登记 | docs/worklog/worklog.md |

- 验收操作层面备忘：本次「测试 IPC 通路」按钮以代码链路审查替代 GUI 实点（黑盒启动验证已覆盖窗口/进程/端口）；建议 ③ 用户确认环节亲自点击一次按钮，预期显示「主进程响应：pong ✓」。
