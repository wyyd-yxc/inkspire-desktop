## 发现的问题

### 🔴 严重

**#1 注入方向用错字段（chapterNo vs sortOrder），可能导致前章事实"漏注入"或"后章事实泄露"**
- 文件：`src/renderer/src/components/ChapterEditor.vue` 中 `memoryCache` computed
- 现状：UI 端用 `props.chapter?.sortOrder` 做"当前章序号"，过滤条件 `m.chapterNo >= sortOrder` 跳过；
- DAO 端（`listMemoriesBefore`）用 `chapter_no < ?`，但该函数在 diff 中**没有任何调用点**（grep 整个 diff 未见 `listMemoriesBefore` 的引用），意味着注入过滤 100% 依赖 UI 端的 sortOrder；
- 用户在 MemoryView 中录入记忆时使用的是「自第几章起成立」（即 `chapterNo`），而章节侧栏的 `sortOrder` 是用户拖拽排序后的位置序号，**两者不等价**：
  - 若用户插入一个中间章节（新章节 sortOrder=3），原本 sortOrder=3 的章节变成 sortOrder=4，但其记忆 `chapterNo=3` 不变 → 注入第 4 章时 sortOrder=4，会跳过 chapterNo=3 的记忆 → **前章事实被遗漏**
  - 若记忆 `chapterNo=5` 属于"终章"，但用户在第 2 章就编辑过、sortOrder=2，生成 sortOrder=3 的章节时会跳过 chapterNo=5 ✓；但用户若把 chapterNo=5 的记忆错录到 chapterNo=2 → sortOrder=2 < sortOrder=3 → **后章事实注入到前章，剧透**
- 验收点 #5 的"前章事实遵守、后章事实不泄露"在两种口径不一致时**不可靠**。
- **建议**：要么让 UI 端改用 `chapter.chapterNo`（与 DAO 对齐），要么在 DAO 层真正调用 `listMemoriesBefore(bookId, chapter.chapterNo)` 作为权威源；并在 `ChapterSidebar.vue` 的记忆录入 UI 里把"自第几章起"标注为"章节序号"而非"排序位置"，或直接禁用对中间章节的记忆录入。

### 🟠 中等

**#2 自测材料存在数据失真风险："359 字"叙述与"1200 字预算"无对照**
- 文件：自测声明 第二章续写 359 字
- 实际注入预算 1200 字，但自测未给出注入文本的实际长度、未给出模型完整 systemPrompt 是否真的包含 memory 段（diff 中 `aiWriting.ts` systemPrompt 的 `wiki` 段拼装可判 ✓，但 memory 段插入位置在 wiki 之后、`要求`段之前，结构合理）
- **可判定**：prompt 拼接逻辑正确
- **无法判定**：实际注入字符数与"是否被模型利用"（已在"已知边界"中说明）

**#3 AI 抽取提示词 diff 被截断，关键白名单/字段清洗规则未审到**
- diff 在 `memoryPrompts.ts` 第 56 行截断（`…严格输出如下 JSON 数组…` 后内容缺失）
- 验收点 #4 的"五类白名单 + 字段值禁双引号"规则**无法在 diff 中独立确认**，需提交方补齐该文件或声明已落实

**#4 `updateMemory` 的 `kind` 字段无白名单校验**
- 文件：`src/main/db/memories.ts` `updateMemory`
- 现状：`kind: (input.kind ?? (row.kind as MemoryKind)) as string` — IPC 直接信任前端传入
- 风险：前端可注入 `kind: 'evil_thing'`，污染筛选与提示词
- **建议**：在 `updateMemory` 与 `createMemory` 中对 kind 做白名单校验（`['plot','stage','character','relationship','clue']`）

**#5 DAO 缺少 kind 白名单与 source 白名单**
- `createMemory` 的 `kind` 与 `source` 都直接落库无校验
- 同样建议在 DAO 层加 enum 白名单

### 🟡 轻微

**#6 删除确认弹窗未在 diff 中体现**
- 验收点 1 要求"删除确认"，但 MemoryView.vue diff 未提供，无法判定
- 自测声明仅说"remove→finalCount"，未涉及 UI 二次确认

**#7 章节重排后 chapterNo 不自动跟随 — 已在"已知边界"声明**
- 与问题 #1 同源：UI 用 sortOrder 但 DAO 用 chapterNo，重排时记忆会"穿越时间线"
- 至少应在 MemoryView 中对每条记忆显示其实际绑定的 chapterNo，避免作者误以为 sortOrder=5 的章节会自动套用 chapterNo=5 的记忆

**#8 `loadMemory` 缺少 `wikiLoadSeq` 同款的"组件销毁后到达的加载结果直接作废"机制**
- `wikiLoadSeq++` 在 `onBeforeUnmount` 中存在
- `memoryLoadSeq` 在 `loadMemory` 内部 `++`，但 `onBeforeUnmount` 中未自增 → 组件销毁后再回来时旧请求仍会写入 → **可能出现幽灵记忆**
- **建议**：在 `onBeforeUnmount` 中加 `memoryLoadSeq++`

**#9 `memoryCache` computed 在 budget 不足时"截断后续"，但未做按优先级裁剪**
- 简单按列表顺序截断，若 plot 类排在最后可能放不进去
- 不构成缺陷，属设计取舍
