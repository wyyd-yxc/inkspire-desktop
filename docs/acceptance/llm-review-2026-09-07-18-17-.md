## 结论（有条件通过）

代码实现了 M10.6/M10.7 的核心功能并对二轮审查遗留的严重问题进行了处置，逻辑基本闭环。但代码静态审查发现 `normNameDup` 正则实现存在明显遗漏（未过滤左方括号），且核心修订去重逻辑因 diff 截断无法完全核实，需修复明确 Bug 并补充验证后方可闭环。

## 逐项核对

1.  **M10.6 词条质量（查重兜底）**
    *   **核对点**：后端 DAO 层是否实现 `findDuplicate` 及规范化比较。
    *   **判定**：**达成**。`src/main/db/wiki.ts` 新增 `findDuplicate` 函数，并在 `createWikiEntry` 和 `updateWikiEntry` 中调用，实现了五入口统一的兜底逻辑。
    *   **疑点**：`normNameDup` 中的正则表达式似乎遗漏了对 `[`（左方括号）的转义，导致 ASCII 方括号可能无法被过滤（详见问题部分）。

2.  **M10.7 正文中枢联动（剧情提取）**
    *   **核对点**：是否新增 `plot_watermark` 及对应同步逻辑。

3.  **二轮遗留处置：严重-1（跨标签文本替换）**
    *   **核对点**：是否登记为已知边界。
    *   **判定**：**符合**。材料已明确登记为“已知边界”，理由（UI 无来源、失败模式安全）在静态分析下成立。

4.  **二轮遗留处置：严重-2（同章多修订竞态/计数误导）**

## 发现的问题（含严重级别）

1.  **【一般】`normNameDup` 正则表达式存在转义遗漏（`src/main/db/wiki.ts`）**
    *   **位置**：`normNameDup` 函数中的 `replace` 正则。
    *   **详情**：正则字符串为 `/[...[\]{}...]/g`。在 JavaScript 正则字符类 `[]` 中，`[` 通常不需要转义，但如果要匹配字面量 `[`，建议显式转义 `\[` 或置于开头。当前写法 `[\]` 在正则解析时会被视为“匹配字面量 `\` 或 `]`”，导致 ASCII 左方括号 `[` 实际上**未被包含**在过滤列表中。
    *   **影响**：如果词条名包含 ASCII 方括号（如 `[草稿]张三`），规范化后将保留方括号，可能导致本应判重的词条未能判重（例如与 `张三` 比较）。
    *   **建议**：修改正则为 `/\[...\]/g` 显式匹配，或将 `[` 移至字符类开头 `[/[...]/g`。

2.  **【一般】`findDuplicate` 全表扫描性能风险（已知边界）**
    *   **详情**：材料已登记该问题（一般-1）。代码实现确为 `SELECT ... all` 后内存遍历，对于单书词条量极大的场景存在性能隐患。既然已登记且属于“一般”级别，验收通过，但建议后续版本增加数据库层索引或查询优化。

3.  **【提示】`wiki:check-dup` IPC 参数校验顺序（`src/main/ipc/wiki.ts`）**
    *   **详情**：校验了 `bookId`/`name`/`type` 为 string，但 `excludeId` 未校验。虽然 `findDuplicate` 内部有 `if (excludeId && r.id === excludeId)` 的逻辑可处理 undefined，但作为 IPC 边界，建议对可选参数也进行类型合法性校验（防止传入对象等意外类型）。
