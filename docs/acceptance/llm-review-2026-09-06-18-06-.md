## 发现的问题

### 🔴 严重

**#1 mergeWatermarkChapter 事务并非真正 ACID，存在回滚失效风险**

```ts
const tx = d.transaction(() => {
  const row = d.prepare('SELECT value ...').get(key)
  // ... 解析 / 合并 map
  setSetting(key, map)   // ← 在事务内部又调用了另一个写函数
})
tx()
```

- `setSetting` 自身不是注册的 `d.transaction()` 函数。当 better-sqlite3 的 `tx()` 包裹一个匿名函数时，事务边界是**函数调用栈**，被调函数若未通过 `d.transaction(fn)` 注册则其内部 BEGIN/COMMIT 不会嵌套——实际上这里依赖 better-sqlite3 的隐式 savepoint 行为。
- 更准确的问题：`setSetting` 内部 `INSERT OR REPLACE INTO settings`，如果 settings 表上未来加了唯一约束或其他触发器，或 better-sqlite3 版本升级改变了嵌套语义，原子意图会静默失效。
- **建议**：要么把 `setSetting` 内的 SQL 内联到事务体里，要么把 `setSetting` 本身改为 `d.transaction()` 注册函数（且不显式 BEGIN）。
- **影响等级**：高（这是三轮审查的核心整改点，不能"看起来对"）

### 🟡 中等

**#2 `sync.ts` IPC 参数校验缺失 wordCount 类型/NaN 兜底**

```ts
ipcMain.handle('sync:watermark-merge', (_e, key, chapterId, wordCount) =>
  wrap(() => {
    if (typeof key !== 'string' || !UUID_RE.test(chapterId)) throw new Error(...)
    mergeWatermarkChapter(key, chapterId, wordCount)
```

- `wordCount` 仅靠下游 `Number.isFinite` 检查，但 `wrap` 之前未做基本类型断言。渲染层若误传 `string`/`undefined`，会在 `mergeWatermarkChapter` 内的 `Number.isFinite(wordCount)` 触发字符串→数字强转（`Number.isFinite("100")` 为 true），导致脏数据入库。
- **建议**：在 IPC 入口也校验 `typeof wordCount !== 'number'`。

**#3 `chapters:list-meta` / `chapters:get` 未做权限/作用域校验**

- `chapters:get(id)` 接任意 string id 直接返回完整 chapter（含 content）。若 renderer 被注入或前端 XSS 拿到 `window.api`，可跨 bookId 读取任何章节正文。
- 前置的 `chapters:list(bookId)` 已有 bookId 入参（即便不做归属校验，至少知道意图上下文），而 `chapters:get` 是单 id 直查，**无任何 bookId 上下文**，是更宽的暴露面。
- 建议：要么加 bookId 参数并校验归属，要么明确文档"trust renderer"模型。M10.5 既然在做权限收紧，此处是明显遗漏。

**#4 `ALLOWED_SETTING_KEYS` 新增的 4 个 sync.* 键与"水位下沉专用 IPC"的设计自相矛盾**

- 上一轮审查专门把水位合并下沉到 `sync:watermark-merge` 专用通道，理由是"消除渲染层 get→set 交错丢更新"。
- 现在又把 `sync.memory_watermark` / `sync.wiki_watermark` 加回 `settings:set` 白名单——意味着渲染层依然可以通过 `setSetting` 直接覆盖整个水位 map，**专用 IPC 的保护等于作废**。
- 低危-1 登记"不改"的同时，这里又把白名单往危险方向扩。**建议**：水位两键应从 `ALLOWED_SETTING_KEYS` 中**移除**，仅保留 `sync.auto_*`（这些确实是设置）。
