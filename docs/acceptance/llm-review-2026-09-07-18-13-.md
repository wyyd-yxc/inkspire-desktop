# LLM 审查（glm-5）

> 材料来源：material-M10.6-M10.7-r2.md

## 结论（有条件通过）

核心功能逻辑基本闭环，一轮审查盲区已补齐，书名号过滤整改到位。但**反向同步（正文替换）存在严重逻辑缺陷，无法处理跨标签的文本替换**（如 `<b>张</b>三`），且同一章节多处修订的串行处理存在潜在的竞态冲突风险，需修复后方可完全通过。

## 逐项核对

1.  **M10.6 词条整理（去重/引用转移）**
    *   **判定：材料足以证明达成，存在技术债。**
    *   `normNameDup` 实现了书名号等符号过滤，符合整改要求。
    *   `findDuplicate` 采用全表扫描 + 内存遍历，虽已登记为技术债，但逻辑上能完成查重功能。
    *   `useWikiCleanup` 的合并逻辑（引用转移、摘要拼接）代码完备。

2.  **M10.7 反向同步（正文定点替换）**
    *   **判定：存在严重设计缺陷。**
    *   `replaceInHtml` 遍历 `TEXT_NODE` 并对 `child.textContent` 进行 `split/join`。
    *   **疑点/缺陷**：如果目标文本被 HTML 标签截断（例如 `oldValue="张三"`，但 HTML 为 `<b>张</b>三`），此时文本节点分别为 "张" 和 "三"，均不包含 "张三"，导致替换失效。这对于富文本正文是极常见的场景，属于核心功能失效。

3.  **M10.7 剧情提取（水位/去重）**
    *   **判定：材料足以证明达成。**
    *   `usePlotSync` 实现了基于水位的章节筛选与推进，逻辑闭环。
    *   `isWikiNameDup` 复用于标题去重，口径一致。

4.  **一轮问题处置**
    *   **书名号过滤**：已核实 `normNameDup` 正则包含 `《》〈〉【】〔〕`，整改有效。
    *   **源码补齐**：核心文件已提供，盲区消除。

## 发现的问题

### 严重-1：反向同步无法处理跨标签文本（功能失效）
*   **位置**：`src/renderer/src/composables/useReverseSync.ts` -> `replaceInHtml`
*   **描述**：代码通过遍历 DOM 树的 `TEXT_NODE` 进行替换。若正文中的实体名被格式化标签截断（如 `“<b>林</b>昭”`），代码读取到的独立文本节点为 `"林"` 和 `"昭"`，无法匹配完整的 `oldValue="林昭"`，导致替换静默失败。
*   **建议**：应在更高层级（如对父元素的 `innerText` 或合并后的文本流）进行匹配与定位，或采用 Range API 重构替换逻辑，确保跨越标签边界的文本也能被正确替换。

### 严重-2：同一章节多处修订的竞态覆盖风险
*   **位置**：`src/renderer/src/composables/useReverseSync.ts` -> `applyEdits`
*   **描述**：当用户勾选同一章节的多条修订（Item A 和 Item B）时，代码串行执行：`get -> replace -> update`。
    *   若 Item A 的替换修改了 Item B 所依赖的 `quote` 原文，Item B 执行时 `replaced` 将为 0 并被跳过。
    *   用户界面表现为：勾选了两项，只生效了一项，且无明确的“冲突/跳过”提示（仅有通用的“跳过 N 处”）。
    *   存在潜在的逻辑冲突（例如 A 改“张三”为“李四”，B 改“张三”为“王五”）。
*   **建议**：在 `applyEdits` 开始前，对同一章节的修订项进行合并处理（基于原始内容一次性应用所有 diff），或在运行时检测到原文变化时给出明确的冲突提示。

### 一般-1：`findDuplicate` 全表扫描性能隐患
*   **位置**：`src/main/db/wiki.ts` -> `findDuplicate`
*   **描述**：虽然已登记技术债，但 `SELECT` 全表后在 JS 层遍历过滤，随着书籍词条量增加（如导入外部大纲产生数百条），可能引发 IPC 通信阻塞。
*   **建议**：考虑在数据库增加归一化名称列并建索引，彻底根除该隐患。

### 一般-2：替换计数语义偏差
*   **位置**：`src/renderer/src/composables/useReverseSync.ts` -> `replaceInHtml`
*   **描述**：`replaced` 变量统计的是“受影响的文本节点数”，而非“实际替换次数”。若一个节点内有两处“张三”，`replaced` 仅 `++` 一次，但实际替换了两次。Toast 提示“已应用 X 处修改”易误导用户。

## 无法判定项

1.  **AI 防幻觉校验的实际拦截率**：
    *   `useReverseSync` 中的 `plain.includes(hit.quote)` 依赖 `htmlToText` 的输出。若 AI 输出的 `quote` 包含 HTML 实体（如 `&amp;`），而 `htmlToText` 已将其解码为 `&`，则校验通过；反之可能误判。需运行验证各种边界情况。

2.  **富文本复杂结构的渲染完整性**：
    *   `replaceInHtml` 直接操作 `doc.body.innerHTML`，对于复杂的 DOM 结构（如嵌套列表、代码块）是否存在破坏性，需运行验证。
