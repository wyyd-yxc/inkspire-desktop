## 发现的问题

### P0-1（阻断）创世台定风/定魂/布局 UI 保存全部静默失败：Vue 响应式对象无法跨 IPC 克隆

**现象**：在创世台通过真实 UI 操作保存「定风」「定魂」「布局」三步时，DB 不落任何记录，页面弹 toast `An object could not be cloned.`，但 UI 本地态即时更新（误显示「已绑定」/打勾），极具迷惑性。仅「造世冷启动」「执笔」两步能落库。

**根因**：`src/renderer/src/views/GenesisView.vue` 的 `saveStep()` 把 Vue 响应式 ref 的 `.value`（`step1.value` / `step2.value` / `step4.value`，均为 reactive Proxy）直接作为 `data` 传给 `window.api.genesis.saveStep()`，经 `ipcRenderer.invoke` 跨进程序列化时，Electron 结构化克隆算法（structured clone）无法克隆 Vue 3 的 reactive Proxy，抛 `An object could not be cloned.`，被各步的 `try/catch` 吞为 toast.error，不落库。

而能落库的两步恰好绕开了响应式对象：
- step3 `acceptWorldColdStart` 传的是新建普通对象 `const world: Step3World = { ...parsed, generatedAt }`（`parseWorldColdStart` 返回纯对象）
- step5 `startWriting` 传的是字面量 `{ started: true }`

**定位**：`src/renderer/src/views/GenesisView.vue`
- `saveStep(step, data, isDone)`（L110-114）：`data` 形参直接转交 IPC
- `selectStyle`（L117-125）传 `step1.value`
- `saveSoul`（L128-135）传 `step2.value`
- `saveLayout`（L235-243）传 `step4.value`

**修复建议**：在 `saveStep` 内对 `data` 去响应式后再传 IPC，任选其一：
- `import { toRaw } from 'vue'`，`window.api.genesis.saveStep(bookId, step, toRaw(data), ...) `（嵌套对象需深去响应式，可用 `JSON.parse(JSON.stringify(data))` 或递归 `toRaw`）
- 或在 `saveStep` 入口 `const plain = JSON.parse(JSON.stringify(data))`

**为什么开发自测漏掉**：自测脚本 `tmp/m5-verify.mjs` 直接用 IPC `window.api.genesis.saveStep(bookId, 1, { styleId, styleName }, true)` 传**普通对象**字面量（L41-44、L48-55、L61-62），绕过了 Vue 响应式层，故自测全绿；而真实 UI 路径必经响应式对象，问题仅在黑盒 UI 验收时暴露。这正是本里程碑「独立子代理黑盒验收」的价值所在。

**影响范围**：直接致验收点 1/2/3/5/重启持久化 不通过；间接致验收点 7（M4 接通）在真实 UI 路径下失效——因 step1/2/4 不入库，`ChapterEditor.loadGenesis` 读不到文风/定魂/写作规则，`aiWriting.systemPrompt` 无设定注入。

### P1-1（一般）M4 设定注入链路本身正确，但被 P0-1 掩盖

实测验证（用 IPC 直接写入 step1/2/4 模拟修复后状态）：写一段中性前文（不含人名/剑灵/灵力），发起 AI 续写，输出 622 字，命中设定关键词「剑灵」（来自 step2 金手指 + book.description）。证明：
- `ChapterEditor.loadGenesis`（L42-60）正确加载 step1(styleHint)/step2(soul)/step4(rules) 并缓存
- `aiWriting.systemPrompt`（L30-60）正确注入文风/定魂 logline+金手指+主线/写作规则
- 续写紧扣设定

故 P0-1 修复后，验收点 7 应自动通过，无需额外改动。注意：续写中出现的「陈默」来自 `book.description`（systemPrompt meta 行注入），非 step2——这是预期行为（description 本就是设定来源之一）。

### P2-1（轻微）定魂 AI 辅助采纳后未自动保存

`acceptSoulAssist` 仅把解析结果填入 `step2.value` 表单并 toast「已填入定魂设定，请检查后保存」，但**不自动调用 `saveSoul`**。结合 P0-1，用户即便手动点「保存定魂」也存不下；P0-1 修复后，建议评估是否在采纳后自动保存，减少用户漏点保存的风险。

### P2-2（轻微）步骤条「完成打勾」与 DB isDone 不同步的假象

因 P0-1，UI 步骤条打勾依赖 `steps[i+1]?.isDone`，而 isDone 不入库 → 当次会话内（saveStep 返回值写回 `steps.value`）也不置位（saveStep 抛错未到达 `steps.value[step] = res.data`），故定风/定魂/布局步骤条其实**不打勾**；但定风卡片「已绑定 ✓」是基于本地 `step1.styleId` 判断，仍显示，造成「看起来绑定了实际没存」的混淆。P0-1 修复后此假象自动消失。

## 遗留与建议

1. **【阻断，必须当场修复】P0-1**：`GenesisView.saveStep` 传 IPC 前对响应式 `data` 去响应式（`toRaw` 或 `JSON.parse(JSON.stringify(...))`）。修复后须用**真实 UI 路径**（非 IPC 直调）复验定风/定魂/布局落库 + 重启持久化 + M4 续写注入。
2. 复验时建议保留本报告的「IPC 直调 vs UI 路径」对照方法，作为回归用例，防止同类「自测用 IPC 绕过响应式」的盲区再次出现。
3. P2-1/P2-2 可在 P0-1 修复后一并评估。
4. 代码质量整体良好（注释/类型/规范达标，typecheck 双 0）；M4 注入、造世冷启动、定魂 AI 辅助解析、步骤条跳转、入口路由等非阻断项均实现正确。
