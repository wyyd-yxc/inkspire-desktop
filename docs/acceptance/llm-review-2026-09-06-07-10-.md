## 发现的问题

### 🔴 严重：IPC 层 update/remove 缺失归属校验，与 DAO 层 P1 整改不自洽

**位置**：`src/main/ipc/plot.ts` 中 `plot:update`、`plot:remove`、`plot-edges:update`、`plot-edges:remove` 四个 handler。

**现状**：四个 handler 仅调用 `assertUuid(id)`，未取事件/连线的 `book_id` 与当前会话上下文比对。DAO 层 `updatePlotEvent` / `removePlotEvent` / `updatePlotEdge` / `removePlotEdge` 函数签名也只接 `id`，无 `bookId` 参数。

**风险**：
- 渲染层任意构造 UUID 即可修改/删除**任何书**的事件与连线（即便 UUID 难以枚举，但渲染层已被 XSS/供应链污染或调试通道误用即可触发）。
- 与三轮审查 P1 提出的"防跨书借边悬挂行"精神冲突：create 路径已堵，update/remove 路径却仍然敞开，攻击面未闭合。
- 与代码注释"信任边界"自洽性差——既然 DAO create 已加归属校验，说明承认存在跨书攻击面，那 update/remove 不加校验就形成"前门锁、后门开"。

**修复建议**（两种任选）：
1. DAO 改签名 `updatePlotEvent(id, bookId, input)` / `removePlotEvent(id, bookId)`，内部 `WHERE id=? AND book_id=?` 并 `RETURNING` 校验行存在；handler 改签名要求前端传 `bookId`。
2. 或保持 id-only 签名，但 handler 先 `getDb().prepare('SELECT book_id FROM plot_events WHERE id=?').get(id)` 与某个会话级 `currentBookId` 比对（渲染层入口已能拿到 `bookId`，应随 IPC 调用一起传入）。

**严重级别**：🔴 **高**（与本轮 P1 整改主旨冲突，属审查闭环不彻底）

---

### 🟡 中等：`assertWikiRefs` 设计登记的"信任边界"论证薄弱

**位置**：`src/main/ipc/plot.ts` 注释段落。

**问题**：登记称"UUID 随机不可枚举 + 单机单用户信任边界"，但：
- M10 同一文件内 `createPlotEvent` / `createPlotEdge` 已加归属校验，证明开发方意识到该攻击面真实存在；
- 注释把"格式校验"等同为"信任边界"在工程语义上是滑坡——格式校验防的是脏数据，不是越权。
- 与 M7 scenes / sceneEdges 的"同一边际模型"对照需提供 M7 的同样注释做引用，目前材料中未附 M7 注释原文，无法验证一致性。

**修复建议**：注释应明确"为何 create 要校验、update/remove 不校验"的取舍逻辑（例如 update/remove 暂以 renderer 单书态上下文兜底），并对应在 handler 处强制要求 `bookId` 入参做二次校验；或在 DAO 层补齐 update/remove 的归属查询。

**严重级别**：🟡 **中**（逻辑漏洞 + 文档可信度）

---

### 🟡 中等：`freeRowYAfter` 5 行避让可能在密集场景仍重叠

**位置**：`src/renderer/src/composables/usePlotAi.ts` 的 `freeRowYAfter`。

**问题**：固定 `for (let tries = 0; tries < 5; tries++)`，如果 5 行内都被占，第 5 行仍返回（未抛错也未标记），会出现"延伸事件与已存在事件完全重叠"。配合 `COALESCE(MAX(pos_x),0)+340` 的默认落位，连锁触发后**视觉上**可能堆叠成一团。

**修复建议**：5 行后仍冲突则回退为最大 `pos_y + 220`，或抛 `console.warn` 并把 `isFallback=true` 暴露给 UI 提示用户手动挪位。

**严重级别**：🟡 **中**（用户可见的功能瑕疵，需运行验证实际触发概率）

---

### 🟢 轻微：`stopEverything` 注释中"旧流交叠"语义需对齐状态机

**位置**：`usePlotAi.ts` 的 `stopEverything`。

**现状**：删去 `isBusy.value = false`，改由 `startPlotGen` 的 `finally` 统一释放。注释解释合理。

**残留疑问**：若 `activeSession?.abort()` 后 `finally` 因异常未执行（例如 startPlotGen 抛同步错，根本没进入 try），`isBusy` 会卡死。需在 `stopEverything` 内补一个 `try { ... } finally { /* noop */ }` 兜底，或在 abort 后调用 `startPlotGen` 的 `abort handler` 显式 `isBusy.value = false`（即便没进入流也安全）。**此为静态不可判定项**，需结合 `startPlotGen` 完整源码确认控制流。

**严重级别**：🟢 **轻**（疑似缺陷，需运行验证）

---

### 🟢 轻微：DAO `removePlotEvent` 未校验存在性

**位置**：`src/main/db/plot.ts` `removePlotEvent`。

**问题**：返回 `.changes > 0`，删除不存在 id 时返回 `false` 而非抛错，与 `updatePlotEvent` 抛「剧情事件不存在」风格不一致，可能让 IPC 层误报成功。

**严重级别**：🟢 **轻**（一致性瑕疵）
