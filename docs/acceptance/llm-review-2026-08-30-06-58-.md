## 发现的问题

### 🔴 严重（必须修复）
1. **package.json 版本跳跃无依据**：`0.1.0 → 0.6.0`，但 M6 是第 6 个里程碑，单独把版本与里程碑号耦合不规范；且 M5 之前的版本历史不可见。若之前已有版本管理约定则无问题，否则属规范违背。
2. **未验证的回归修复声明**：材料自测「修复了 stale bookId」并提示「请专门测试 A→B 跨书导航」，但本次 diff **完全不包含 `WikiView.vue / GenesisView.vue / WorkspaceView.vue` 三个被点名组件的修改**。即声称修了 stale bookId，却没看到修复代码——验收材料与代码变更不一致，**不可接受**。
3. **幂等判定逻辑不明**：`material-M6-wiki.md` 反复强调「重复导入不重复建」，但 `wiki.ts` 仅暴露通用 `list/create`；是否存在「按 (bookId, type, name) 查重再创建」的导入专用函数？diff 未显示该函数，**幂等达成路径不可静态证实**。

### 🟡 中等（应改进）
4. **`updateWikiEntry` 的浅合并陷阱**：`{ ...existing, ...input }` 后单独覆盖各字段，看似安全，但 `attributes/relations` 若传 `undefined` 不会被覆盖（用了 `!== undefined` 判断），**这是好的**；然而若调用方传 `[]` 显式清空是 OK 的——逻辑正确，但缺少注释说明「传 undefined 不修改，传空数组清空」的不变量，易被误改。
5. **`removeWikiEntry` 返回值语义**：返回 `boolean`，preload 暴露类型为 `Promise<IpcResult<boolean>>`，但前端调用方拿到 `false` 时无法区分「词条不存在」与「删除失败」。建议抛错或返回删除的词条。
6. **`WikiRow.type` 类型断言不安全**：`r.type as WikiType` / `r.system_role as WikiSystemRole` / `r.injection as WikiInjection` 均无运行时校验。若 DB 因手动编辑或迁移 bug 写入脏数据，会一路穿透到 UI。应在 `toEntry` 处加白名单校验/默认回退。
7. **`electron-builder.yml` 改动风险**：`npmRebuild: false` + `asarUnpack` 显式声明 better-sqlite3 prebuilds。注释解释合理，但**生产打包实际能否加载 native 模块**未在材料中验证（仅声明「dev 模式已验证」）。属潜在打包事故。
8. **ChapterSidebar.vue diff 被截断**：无法判断侧栏「百科」入口是否被正确加入工作台侧栏（验收点 5 的入口要求）。

### 🟢 轻微（建议）
9. **`parseJson` 静默吞错**：`try/catch` 直接 `return fallback`，DB 中的非法 JSON 会悄无声息丢失数据，建议至少 `console.warn`。
10. **数据库迁移幂等性**：v5 用 `CREATE TABLE IF NOT EXISTS`，OK；但若未来要改 `wiki_entries` 字段，需新建 v6。**无 schema 版本化校验代码**（`PRAGMA user_version` 写入逻辑），需确认 `database.ts` 现有迁移机制是否已有此保障（diff 未显示）。
11. **`loadWiki` 内的 N+1 查询**：`res.data.find((x) => x.id === r.targetId)` 在 `always` 词条循环内对 `relations` 查找，每次 O(N)，最坏 O(N²)。词条规模小可忽略，但应记入技术债。
12. **`wikiLoadSeq` 竞态防护不完整**：用 seq 防止过期结果覆盖，但**未捕获 `await` 之间组件已销毁的情况**，无 `onUnmounted` 清理。若 bookId 快速切换可能产生 zombie 任务。

### 审查建议（对开发方）
1. **必须补齐**：stale bookId 修复的三文件 diff，以及 WikiView.vue、wikiPrompts.ts、aiWriting.ts 的相关 diff，否则本验收**无法以静态方式通过**。

4. 生产包构建（`npmRebuild: false`）建议在 CI 上跑一次完整打包并启动验证。
