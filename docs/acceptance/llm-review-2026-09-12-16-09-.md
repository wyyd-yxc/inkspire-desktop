# LLM 审查（glm-5.1）

> 材料来源：material-M15-bindings.md

## 结论
有条件通过 —— 核心数据层与解析逻辑实现扎实，但存在 UI 状态同步隐患及 diff 截断导致的调用点覆盖盲区，需补充完整 diff 与轻微修复后全量通过。

## 逐项核对
1. **两档案不同模型时各槽位请求路由到各自绑定档案**：
   - **可判定**：代码逻辑实现了 `resolveProfileForSlot(slot)`，其内部按照“槽位绑定 → 默认档案 → 首个档案”的顺序解析，并在 `generateWriting` 增加必传 `slot` 参数强制归槽。
   - **疑点**：材料提供了 14 个调用点清单，但 diff 截断，仅展示了 `ChapterEditor`、`AssistantDock`、`StyleDigestDialog`、`useAutoSync` 等少量文件，无法静态核对剩余 11 个调用点是否全部且正确地传入 `slot`。
2. **未绑定槽位回落默认；删绑定回落**：
   - **可判定**：`agentSlots.ts` 中未匹配到绑定则回落 `defRes.data`；`setBinding` 中传入 `''` 时执行 `DELETE` 语句，逻辑严密。
3. **删除档案后对应槽位绑定级联清零、回落默认不报错**：
   - **可判定（SQL 逻辑）**：Migration v15 明确声明 `REFERENCES api_profiles(id) ON DELETE CASCADE`。
   - **无法判定（运行时）**：SQLite 的 FK CASCADE 严重依赖 `db.pragma('foreign_keys = ON')` 的运行时状态，静态代码无法确保其被执行且未被覆盖。
4. **绑定重启持久**：
   - **可判定**：数据通过 `better-sqlite3` 落盘至 `agent_bindings` 表，重启后必然可读。
5. **设置分区 8 行渲染+即改即存**：
   - **可判定**：`SlotBindingsSection.vue` 通过 `v-for="slot in AGENT_SLOTS"` 渲染行，`@change="onPick"` 触发 IPC 写入，并在保存期间 `:disabled="saving !== ''"` 全局禁用防重复提交。符合设计要求。
6. **typecheck 三重闸门+console 零报错+自测零外部 AI 消耗**：
   - **无法判定**：属于运行时与黑盒范围，只能信任开发自测声明。

## 发现的问题
1. **[中危] UI 状态同步隐患（保存失败时未重置交互态）**：
   - **位置**：`src/renderer/src/components/settings/SlotBindingsSection.vue` 的 `onPick` 方法。
   - **缺陷**：当 `window.api.bindings.set` 请求失败抛出异常进入 `catch` 块时，仅执行了 `toast.error`。由于此时未调用 `await load()` 刷新数据，Vue 响应式绑定 `:value="boundId(slot)"` 的底层数据未变。但原生 `<select>` 的 DOM 选中项已被用户手动改变，虽然 Vue 会在下一渲染周期纠正 DOM，但在慢速机器或特定时序下，用户会观察到“下拉框显示为新值但 Toast 报错保存失败”的割裂状态，且无法直观获知当前数据库的真实绑定。
   - **建议**：在 `catch` 块末尾追加 `await load()` 以强制拉取真实状态重置 DOM，或在失败时显式回滚 `e.target.value`。
2. **[低危] 类型安全误导（IPC 边界类型注解）**：
   - **位置**：`src/main/ipc/bindings.ts`。
   - **缺陷**：`ipcMain.handle('bindings:set', (_e, slot: AgentSlot, profileId: string)` 中给 `slot` 标注了 `AgentSlot` 类型。但 Electron IPC 传输的是 JSON 字符串，此处的静态类型注解会掩盖跨进程边界的类型丢失。虽然有 `AGENT_SLOTS.includes(slot)` 运行时白名单兜底，但更好的做法是入参标为 `string` 并在内部进行类型断言，以提示边界防御。
3. **[低危] 每次生成请求触发 3 次 IPC 查询（性能浪费）**：
   - **位置**：`src/renderer/src/services/agentSlots.ts`。
   - **缺陷**：每次调用 `resolveProfileForSlot` 均通过 `Promise.all` 发起 3 次 IPC（profiles.list, settings.get, bindings.list）。在密集写作场景下存在不必要的 IPC 开销与序列化开销。虽不致命，但可优化为在主进程提供单一 `resolveProfile` IPC 接口或渲染层做短期缓存。
4. **[低危] 材料笔误**：
   - **位置**：材料 `附录 A2` 归槽清单。
   - **缺陷**：`composposables/useWikiCleanup.ts:112` 存在拼写错误（多了一个 'p'），应为 `composables/`。

## 无法判定项
1. **调用点完备性**：因提供的 diff 在 `useMemorySync.ts` 处截断，无法静态核对剩余 11 个 `generateWriting` 调用点及 `chatStream` 直调点（如 `GenesisView`、`CanvasView` 等）是否准确归槽。
2. **FK CASCADE 运行时状态**：无法静态确认 `foreign_keys=ON` 在复杂启动时序中未被其他迁移或连接重置。
3. **测试断言真实性**：材料声明的 `tmp/m15-t1.mjs` 19/19 通过及 0 外部 AI 消耗，属黑盒范围，需运行验证。
