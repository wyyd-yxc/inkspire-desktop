# LLM 审查（glm-5.1）

> 材料来源：material-M14-digest.md

## 结论（有条件通过）

M14 拆书功能的代码骨架与隐私决策基本落地，但材料对核心验收点（正文风格可感知）缺乏黑盒实证，且代码存在「空数据落库」与「前置清洗缺失」等明显缺陷，需整改后方可完全通过。

## 逐项核对

1. **导入参考 txt→AI 拆解→勾选→风格包生成且来源徽标=拆书（source_type='digest' 落库）**
   - **材料是否足以证明**：足以证明。T1 测试明确断言了从原生对话框选文到落库 `sourceType='digest'` 及列表徽标渲染的全链路；代码层面 `styles.ts` 确有白名单校验与 `digest.ts` 通道支撑。
   - **疑点**：T1 声称用 win32 PS1 脚本突破 CDP 限制，材料描述极尽细节，但静态下无法确证其脚本是否真的稳定驱动了原生对话框。

2. **该包绑定新书后生成正文风格可感知（真实 AI 特征断言——黑盒覆盖）**
   - **材料是否足以证明**：**不足以证明**。材料中 T1/T2 均为假服务器或局部功能测试，T3 仅抽查了「档案拆解」的产出，完全没有涉及「绑定新书 → 生成正文」的黑盒覆盖断言。此验收点处于未验证状态。

3. **全不勾确认禁用/取消/拆解失败均不落库；参考文本重启后无任何残留**
   - **材料是否足以证明**：部分证明。T2-a/b/c/e/f 覆盖了边界与失败不落库场景，代码层面 `StyleDigestDialog.vue` 也在关闭时清空 `pick.value`。
   - **疑点**：材料声称「未勾选正文零残留（主库+WAL 文件字节级搜索）」，但代码中没有任何持久化逻辑，此断言显得多余且静态无法验证其搜索严谨度。

4. **超 2 万字截断生效（只取开头）**
   - **材料是否足以证明**：足以证明。T2-d 明确断言了截断后的字数及头部/尾部标记特征；代码 `digest.ts` 中 `raw.slice(0, DIGEST_TEXT_LIMIT)` 逻辑与之吻合。

5. **删 digest 包走既有解绑链路（FK SET NULL 回落）**
   - **材料是否足以证明**：足以证明。T2-g 验证了回归，且 diff 未触动既有删除链路，逻辑自洽。

6. **typecheck 三重闸门+console 零报错；AI 用例重试≤3**
   - **材料是否足以证明**：部分证明。声明 typecheck 绿及 console 零报错。
   - **疑点**：材料中**完全未体现**「AI 用例重试≤3」的约束验证，此子项无法证实。

## 发现的问题

1. **【中等】渲染层缺少前置白名单清洗，异常 AI 返回可能撑爆 UI 布局**
   - **位置**：`StyleDigestDialog.vue` `buildCandidates` 函数。
   - **分析**：材料声称 `digestPrompts.ts` 有「渲染层白名单清洗（name ≤30/tone ≤100 等）」作为双保险之一。但 diff 提供的代码中，`buildCandidates` 直接将 `d.tone`、`d.rules`、`d.sample` 塞入候选列表，未见任何长度截断或字符清洗逻辑。若 AI 返回超长内容，虽有 DAO 兜底落库不崩，但前端弹窗渲染可能会被超长文本撑破或导致卡顿。
   - **修复建议**：在 `buildCandidates` 构造 `SyncCandidateItem` 时，对 `title` 字段做长度截断与清洗。

2. **【中等】部分不勾选时，允许核心字段为空字符串落库**
   - **位置**：`StyleDigestDialog.vue` `doCreate` 函数。
   - **分析**：代码 `const tone = checked.find(...)?.title ?? ''` 表明，如果用户在 review 态取消了「调性」的勾选，`tone` 会变成 `''` 并传给 `styles.create`。一个没有调性、可能只有孤立规则的风格包，在业务上是否合法？材料声明「全不勾确认禁用」，但未限制部分核心字段不勾选时的处理。
   - **修复建议**：明确业务规则，若调性为必选，应在 review 态对核心字段做强制勾选校验，或在 `doCreate` 拦截空 tone。

3. **【低】状态切换时序导致体验延迟**
   - **位置**：`StyleDigestDialog.vue` `startDigest` 函数。
   - **分析**：`phase.value = 'running'` 被放在 `await resolveProfile()` 之后。如果 `resolveProfile` 耗时较长或网络异常，UI 仍停留在 `import` 态，用户点击后无反馈。
   - **修复建议**：将 `phase.value = 'running'` 移至 `resolveProfile()` 之前，或增加 loading 态。

## 无法判定项

1. **原生文件对话框自动化真伪**：材料声称使用 win32 PS1 脚本通过 `WM_CHAR` 驱动原生对话框，静态审查无法判定该脚本是否在所有目标平台上稳定运行，也无法判定其是否真的突破了 Electron CDP 的限制。
2. **流式请求的真实中断（abort）有效性**：代码调用了 `session?.abort()`，但 diff 未包含 `chatStream` 的实现。无法判定 abort 是否真的中断了底层网络请求，还是仅仅丢弃了回调（若是后者，可能导致外部 AI 额度无声泄漏）。
3. **`SyncCandidateDialog` 全不勾禁用逻辑**：材料与当前 diff 均未展示 `SyncCandidateDialog` 的内部实现，无法判定其「全不勾确认禁用」的逻辑是否健壮。
4. **真实 AI 拆解质量与正文注入感知（验收点2）**：缺乏相关测试材料，必须通过实际运行连接真实 AI 并生成正文来验证。
