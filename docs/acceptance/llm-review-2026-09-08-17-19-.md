## 发现的问题（含严重级别）

### 1. 严重（流程）：版本号与 Tag 命名严重不符，基准不可信
- **现象**：验收材料声明基准为 `v0.15.1-m10.8-final`，但 diff 显示 `package.json` 版本从 `0.6.0` 变更为 `0.15.0`。
- **分析**：按照语义化版本规范，Tag `v0.15.1` 应对应 `package.json` 中的 `0.15.1`。当前 diff 显示基准版本为 `0.6.0`，说明要么 Tag 打在了错误的 commit 上，要么此前的版本号管理完全失序。材料解释“不同域”理由牵强，这导致后续的版本追溯和回滚机制存在极大隐患。
- **建议**：必须重新校准基准 Tag 与代码版本的对应关系，确保后续发布的可追溯性。

### 2. 中（逻辑）：`listInspirations` 全量拉取策略
- **位置**：`src/main/db/inspirations.ts` -> `listInspirations`
- **问题**：DAO 层查询 `SELECT * FROM inspirations WHERE book_id = ?` 未携带 `is_recycled` 过滤条件，而是返回全量数据交由前端筛选。
- **风险**：在便签数量累积较多（如 >1000）时，全量拉取会造成不必要的 IPC 传输开销和前端内存压力。虽然符合“本地优先”策略，但不符合“数据库做筛选”的最佳实践。
- **建议**：建议增加过滤参数，或在索引 `idx_inspirations_book` 基础上利用 `WHERE is_recycled = ?` 进行下沉筛选。

### 3. 低（规范）：标题空串静默回退
- **位置**：`src/main/db/inspirations.ts` -> `updateInspiration`
- **问题**：`input.title.trim() || existing.title` 逻辑会导致传入空标题时静默回退旧值。虽然 UI 层声称拦截，但这违反了“显式优于隐式”原则，后端应拒绝空标题（抛错）而非静默忽略，以防止 API 直接调用时的困惑。
