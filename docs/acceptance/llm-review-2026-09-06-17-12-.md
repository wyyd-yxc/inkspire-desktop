## 发现的问题

### 严重（P0）

**§1 「P1 修复」并未真正消除竞态——`setWatermarkChapter` 在并发下仍可丢失更新**
材料自述修复方案为"以 DB 最新值为基合并写"。但仔细审 `useAutoSync.silentSyncChapter`：
```ts
change.wikiWatermark = await setWatermarkChapter(WIKI_WATERMARK_KEY, change.wikiWatermark, ch.id, ch.wordCount)
```
这里 `change.wikiWatermark` 是**本次调用 `checkOnce` 入口处一次性 `getWatermark` 取得的快照**；函数内部虽然再读一次 DB 取 `latest`，但并发竞态发生在**两次 `setWatermarkChapter` 调用之间**：调用 A 读 latest→B 读 latest（读到 A 尚未写入的旧值）→A 写、A 拿回 next→B 继续用 B 自己的 old+新章节合并→B 写→**A 写入的章节水位丢失**。
场景具体可构造：用户在工作台手动同步章 A（同步推进）的同时，静默档正在跑章 B，两次 `set` 之间夹一次 `get`，后者把前者的写入读漏。
**建议**：水位必须用单条 SQL `UPDATE … WHERE word_count_expected = ?` 或在主进程做 mutex；当前实现是 read-modify-write，非原子。

### 中（P1）

**§2 关闭/开启自动同步时 `lastCheckAt` 不刷新——重开后立即触发一次**
`tick()` 中 `if (Date.now() - lastCheckAt < s.intervalMin * 60_000) return` 在 `enabled=false` 早返回之前。意味着用户关闭 N 小时后重新开启，第一次 tick 就触发检测，可能在用户预期之外抽完全部积压。规范应：开启瞬间重置 `lastCheckAt = 0` 或干脆 "启用后第一次延迟一个 interval 再触发"。

**§3 `silentSyncChapter` 不消费 `pendingCreates` / `merge` 面板——静默档不弹面板**
材料称"静默档=自动入库（只增不改），单轮 ≤3 章"。但当 AI 抽取的候选全部为重复时：`useWikiSync`/`useMemorySync` 的 `handleParsed` 中 `allDupChapters` 推水位分支仅在**手动调用入口**触发；`useAutoSync.silentSyncChapter` 是**内联**做 `normText` 比对+create，**完全不走 `handleParsed`**。这意味着：静默档重复候选章节**不会推水位**（因为这里根本不会调 `advanceWatermark` 的"全重复推水"分支），下个 tick 仍会反复重抽同章、反复消耗 AI 额度。
**这与材料"应用缺陷修复 #2 P2 混合场景推水缺失"自我声明的修复不一致——该修复只对手动路径有效，静默档（App 级）仍是漏洞。** 严重程度应升级到 P1。

**§4 `ToastHost` 移除 `pointer-events-auto` 类——可能破坏下层交互**
原类 `pointer-events-auto` 在多层 `pointer-events-none` 父容器下确保 toast 可点击；移除后若任何祖先容器（modal、teleport 包装）设置 `pointer-events-none`，toast 会被穿透。`SyncCandidateDialog` 使用 `teleport to="body"`，与 toast 同级，问题被规避；但未来引入的其它浮层可能踩坑。属"破坏性重构无注释"，应明确改回或加注释解释。

**§5 `buildPlotChainText` 在三处重复实现——DRY 违反与维护风险**
- `services/syncService.ts:buildPlotChainText`
- `services/syncService.ts:buildProgressText` / `buildFactsText`
- `ChapterEditor.vue:loadPlot` 内联再次手写同样排序+截断逻辑
- 材料 `usePlotAi.refreshSyncContext` 中又隐含地由 `buildProgressText/buildFactsText` 实现
任一处修改（排序规则、截断算法）会立刻让 4 处行为分叉。应统一收敛到 `syncService`，`ChapterEditor.loadPlot` 直接调用 `buildPlotChainText(events, PLOT_INJECT_LIMIT)`。

### 低（P2）

**§6 设置白名单新增 6 个 `sync.*` 键——含 `sync.memory_watermark`、`sync.wiki_watermark` 两个 JSON 大对象**
- 这两个键会被无差别地从渲染层 `settings.set` 任意写入，等同于把"水位"的可信源交给客户端。攻击面虽在本地 Electron 较低，但**渲染层任何 XSS/依赖链污染**即可注入伪造水位（让"已抽取章节"伪装成"未抽取"，或反向让"未抽取章节"伪装成"已抽取"绕过同步）。
- 建议：水位仅由主进程在 IPC 处理器内部写入（提供专用 IPC 而非通用 settings.set 白名单）；当前实现等于把"同步状态的真相"半暴露给前端。

**§7 `extractOnce` 拿 session 的方式存在 race**
```ts
void generateWriting(messages, {...}).then(({ session }) => { activeSession = session })
```
这是 fire-and-forget——`extractOnce` 的 `await promise` 在 `generateWriting` 内部 `onDone`/`onError` 触发时就会 resolve，但 `.then(({ session }) => ...)` 异步挂载 session。**当 `onDone` 同步触发、用户在解析前点停**，`activeSession` 可能还没被赋值，`stopEverything()` 调 `abort()` 时是 null——只能停掉"尚未发起"的会话，停不掉"已完成正在解析"的会话"。该路径下用户取消操作实际无效。属 UI 体验缺陷，非数据缺陷。

**§8 `useMemorySync.openExtractDialog` 强制 `extractScope='single'`**
每次打开都默认单章而非上次选择；批量入口（M10.5 卖点）需要用户每次手动切。属 UX 而非验收不达标，但材料声明"未抽取章节批量可用且水位准确"——可用≠易用。

**§9 `WikiExtractDialog.vue` 在材料实现定位中列出，但未提供代码，无法静态验证是否同样有 `runProgress` busy 锁、`AbortController` 接入**。

**§10 `silentSyncChapter` 在 `wiki.create`/`memories.create` 失败时不推进水位**（符合设计），但 `throttledError` 直接 `break` 出 `for…of round`——后面"剩余 2 章"也被一并跳过，且下一章的错误不会触发（因为已 break）。设计原意是"失败即停本轮"，但 `jobs.length - round.length` 的"剩余"统计会把"本可正常入库"的章节也算进去，toast 文案误导用户。属文案/UX 问题。
