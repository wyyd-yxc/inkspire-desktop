## 发现的问题

### 🔴 严重（必须修复）

**S1. `@` 触发后输入框不再追加字符时选择器会"粘住"**
- 现状：`onInput` 仅 `if (input.value.endsWith('@')) showPicker=true`，但选择器打开后用户继续输入更多字符时 `endsWith('@')` 为 false，选择器不会自动关闭；需显式 `else showPicker=false` 或在选择 chip 后关闭。

**S2. `clearAssistantMessages` 永远返回 `true`**
```ts
return d.prepare(...).run(bookId).changes >= 0
```
- `changes >= 0` 恒成立（DELETE 即使 0 条也返回 0）。应改为 `> 0` 或改为 `return boolean` 语义明确化，否则清空接口对外毫无信息量。

**S3. `memories.ts` update 路径校验弱化**
- `updateMemory` 中 `kind` 改动走白名单，但 `chapterNo` 仅 `Math.max(1, Math.round(...))`，未校验 `Number.isFinite`；传 `NaN/Infinity` 会得到 `Math.round(NaN)=NaN`，再 `Math.max(1, NaN)=NaN`，写入 DB 后读取映射为非法值。需补 `Number.isFinite` 守卫，与 `createMemory` 对齐。

**S4. assistant IPC 缺乏 bookId 存在性/权限校验**
- `assistant:create` 直接信任 `bookId` 字符串，若渲染端传空串或越权 bookId（跨书写入），DAO 仅依赖 FK 报错。对比 `memories:create` 接收完整 input 对象有更多上下文，assistant 通道建议至少做非空/UUID 格式校验，并依赖 `books` 表存在性预检或返回明确错误。

### 🟡 中等（建议修复）

**M1. 流式中断后数据库可能残留"半条" assistant 消息**
- 截断前未看到 onAbort/onError 时的 `assistant:create` 回滚/补全策略。若流式中途断网/用户按停止，pending 气泡与 DB 真实记录的一致性未在材料中体现。

**M2. `systemPrompt` 拼装缺失可见证据**
- 验收点 3/4/5 都依赖 systemPrompt：章节标题、2000 字正文截断、wiki 词条设定注入、`selectionText` 注入。diff 中 `AssistantDock.vue` 在这些逻辑之前即被截断，**无法静态确认其实现**。属"需运行验证"项，但材料应至少附上该函数。

**M3. 浮球仅在 WorkspaceView 挂载的边界**
- 切换至非正文工作台（如世界观/人物卡）后浮球消失，是否需要保留对话上下文（DB 已按 bookId 隔离，可恢复），文档未说明行为。

**M4. 对话上下文"最近 20 条"与 DB"50 条"语义割裂**
- 文档说"上下文窗口最近 20 条，DB 保存 50 条"，但 `listAssistantMessages` 默认 limit=50，调用方负责再截前 20。若渲染端漏截，会把 50 条全量注入 system/messages，违反设计。应在 DAO 或 IPC 层提供 `listForContext(bookId, n=20)` 区分持久化与上下文视图。

**M5. `@` 选择器未防抖/未处理空词条集**
- 空书（无 wiki 条目）时 `@` 仍弹出空白面板，无引导；建议无条目时禁用触发或显示"暂无百科条目"。

**M6. `selectionText` 大小未限**
- 选区感知未声明最大长度阈值；用户拖黑全本（几万字）将一次性注入 prompt，存在 token 超限与体验卡顿风险。

### 🟢 轻微（建议）

**L1.** `memories.ts` 的 `listMemoriesBefore` 注释自承"预留，当前未使用"，属于死代码，建议删除或加 `// @reserved`。
**L2.** 迁移 v8 `memories` 与 M9 助手无直接关系，却随本次提交合入；按变更粒度原则应拆分 PR，便于回滚。
**L3.** `createAssistantMessage` 抛错信息 `'消息内容不能为空'` 与 `createMemory` 风格一致，但 `assistantMessages.ts` 缺对应的 service 层单元测试自测声明。
**L4.** `assistantMessages.role` 字段无 CHECK 约束（`memories.kind` 有白名单），建议 migration 追加 `CHECK(role IN ('user','assistant','system'))`。
