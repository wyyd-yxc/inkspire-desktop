## 发现的问题

### 🔴 严重（影响通过判定）

**D1. 承诺的"附录 E 自测原始输出全文"在 r2 材料中未提供**
- 整改 diff 中 §1 项下"回归证据"声称"附录 E（T1 18/18 最终回归轮）"，但**本份材料实际止于附录 D（仅摘要）**。
- 一轮审查明确将"T1-T4 断言粒度"列为无法判定项，要求看原始日志；r2 引用了不存在的附录来满足此项。
- **结论**：证据链断裂，必须补充附录 E（含 18/18 断言实际输出）否则 §1 回归不充分。

**D2. settings 键白名单被新增 5 个 sync.* 键，但合并通道仅允许其中 2 个水位键 — 内部矛盾**
- `main/ipc/settings.ts` 新增白名单：`sync.memory_watermark`, `sync.wiki_watermark`, **`sync.auto_enabled`, `sync.auto_interval_min`, `sync.auto_mode`, `sync.auto_targets`**
- `main/db/settings.ts` `WATERMARK_KEYS` 仅含 2 个水位键
- 这意味着渲染层仍可通过 `window.api.settings.set('sync.auto_enabled', ...)` 写入四个调度键，**绕开 sync 域的 IPC 通道**，与 §6"水位仅影响同步调度不碰正文数据"的信任边界模型一致——但 §6 的论证**仅防御了水位伪造，没有防御 auto_* 伪造**。攻击者（在本机信任模型下是用户自己）可任意开关/调整 auto 同步。
- **结论**：不是新增回归（r1 已有这些键的概念），但 r2 整改把这些键显式加入白名单而**未在材料中说明**，属于隐性扩大攻击面却无对应说明。

### 🟡 中等（需澄清，不阻断）

**B1. §2 lastCheckAt 设计权衡的源码证据缺失**
- 反驳"积压全抽"用了"≤3 章/轮硬上限"的说法，但 `useAutoSync.ts` 中该上限的代码片段未附。
- 一轮审查的关切是"首次 tick 立即触发"可能造成用户预期外的网络/AI 调用。回应中"提醒档零 AI 消耗"也未量化（如：是否触发额外 DB 查询？是否发送 IPC？）。
- **建议**：附 useAutoSync.ts 的 tick 调度 + 硬上限所在行号，让审查者直接判断。

**B2. §7 "微任务级 <1ms" 无时序佐证**
- 关键论断："chatStream 在 invoke 返回 requestId 后即 resolve，session 赋值发生在流首个事件之前"。
- 这一说法**正确**（因为 invoke 是 async，session 赋值在 .then 微任务，而流事件通过 IPC event 投递也是微任务，**实际先后顺序取决于具体实现**），但"远晚于赋值"非显然。
- **建议**：附 chatStream 实现的关键 10 行（含 session 赋值位置和 event 发送位置），让审查者自判。

**B3. `setWatermarkChapter` 整改后 `_current` 参数被忽略 — 签名兼容但语义变了**
- 新版 `return { ..._current, [chapterId]: wordCount }` 用旧参数作为返回值基，而实际写入走 IPC 走真值。
- **风险**：调用方如果在 IPC 返回前立刻使用返回值（例如检查其他章节的水位），拿到的将**不是 DB 最新值**，而是调用方自己传入的过期快照。
- 看 useMemorySync / useWikiSync 的调用模式是否依赖此返回值的"新鲜度"。材料未涉及。
- **建议**：要么返回值明确标注为"输入回显"，要么真的 `await getWatermark(key)` 再返回（多一次 IPC 但语义正确）。

**B4. `chapters:list-meta` 暴露 `updated_at` 但未在共享类型注释说明**
- `ChapterMeta` 含 `updatedAt`，渲染层可借此做"最近修改时间排序"或"上次同步时间对比"。
- 一轮材料 § 无法判定 6 涉及变更检测粒度，r2 补充了 list-meta 但**未说明 useAutoSync 变更检测是否真用上 `updatedAt`**（是用 wordCount 差值还是时间戳？材料中说"字数不符"但未明示）。
- **建议**：在 useAutoSync 的 findUnextracedChapters 实现中明示判断字段。

### 🟢 轻微（提示性，不阻断）

**L1. `ChapterSidebar` 新增 sync 按钮的 `syncAlert` 红点 z-index/可达性**
- 按钮紧贴章节标题右侧，红点 `absolute -right-0.5 -top-0.5`；若章节标题过长换行，红点可能被裁剪。无样式验证。

**L2. `PlotAiDialog` 新增 `contextInfo` 行无 prop 必填校验**
- 新增 prop `contextInfo: string` 未标 `required: false` 也未给默认值；若父组件漏传将得到 `undefined`，v-if 守卫正常，但 console 中 props 校验会警告（取决于 Vue 版本）。

**L3. `SyncCandidateDialog` diff 被截断**
- 提供的 diff 在第 100 行左右截断（"…"），看不到 `confirm` 事件的具体 emit 实现和禁用项的勾选逻辑。
- 同步采纳面板是核心交互，**其状态管理、禁用规则、确认回传应可见**。

**L4. `App.vue` 在 `onMounted` 调用 `startAutoSync()` 无清理**
- 若 SPA 路由切换或热重载，组件可能重新挂载，**startAutoSync 可能被多次调用**。需检查 startAutoSync 内部是否幂等（材料未涉及）。

**L5. `mergeWatermarkChapter` 中 wordCount 允许任意有限数 — 包括 0 和负数**
- `Number.isFinite` 通过 `-1`、`0`、`NaN 之外的所有数字`。
- 写入 `wordCount: -1` 会污染水位，导致"过期检测"永远命中该章。
- 在信任边界下这是低危，但与 §6"水位仅影响同步调度"的代价分析（"多余的 AI 调用"）一致 — 仍属已知风险，可不修。
