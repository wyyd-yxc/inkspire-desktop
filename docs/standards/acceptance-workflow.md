# 验收流程规范（Acceptance Workflow）

> 每完成一个功能/里程碑必须走完本流程才算「完成」。三级验收：自测 → 二次验收（独立子代理）→ 用户确认。
> 版本：v1.0 · 制定日期：2026-08-22

## 1. 验收流程总览

```
功能开发完成
  → ① 开发自测（主责：开发模型）
  → ② 二次验收（主责：独立验收子代理）
  → ③ 用户确认（用户亲自体验）
  → ④ git commit + tag → 更新 roadmap/worklog
```

任一环节不通过：修复后从 ① 重新走。

## 2. ① 开发自测清单

- [ ] 功能按 roadmap 验收点逐条核对通过
- [ ] `npm run dev`（或打包后）实际启动操作过，不是「看起来能跑」
- [ ] 异常路径测试：空输入、超长输入、非法操作、断网时的表现
- [ ] 重启应用后数据仍在（持久化验证）
- [ ] 无 console 报错；主进程无未捕获异常
- [ ] 代码符合 coding-standards（注释、命名、类型）

## 3. ② 二次验收（独立子代理）

**目的**：以「新接手者」视角黑盒+白盒复查，开发模型自己不能只给自己验收。

**执行方式（当前）**：开发模型派出一个独立子代理（Agent 工具，general-purpose），子代理：
1. 只读 `docs/`（设计目标、roadmap 对应条目、本规范）建立预期；
2. 审查实现代码是否与文档/规范一致；
3. 实际启动应用执行功能清单（黑盒操作）；
4. 输出结构化验收报告。

**执行方式（升级路径，已启用）**：外部模型审查 + 本地子代理黑盒验收双轨并行：
- **LLM 静态审查**：脚本 `scripts/accept-via-llm.mjs`（2026-08-22 启用）。Key 取环境变量 `OPENROUTER_API_KEY`，缺省回退读 ZCode 配置中的 OpenRouter 档案；默认模型 `stealth/ox-alpha`。开发模型仅准备材料（验收点+diff），不得修改外部模型结论；报告存 `docs/acceptance/llm-review-*.md`。
- **子代理黑盒验收**：本地 Agent（general-purpose）以新接手者视角实际启动应用、执行功能清单（参考其使用 --remote-debugging-port + CDP 驱动真实 Electron 的方法）。
- 两份报告都入库，任一「不通过」即不通过；分歧项由用户裁决。

**子代理提示词必须包含**：本规范路径、目标里程碑、验收点清单、输出模板。

## 4. 验收报告模板

报告存至 `docs/acceptance/YYYY-MM-DD-M<里程碑>-<功能slug>.md`：

```markdown
# 验收报告：<功能名>（M<里程碑>）

- 日期 / 验收人（模型名与角色：开发自测 or 独立验收）
- 结论：**通过 / 有条件通过 / 不通过**（一句话）

## 验收点逐项核对
| # | 验收点 | 结果 | 备注 |
|---|---|---|---|

## 发现的问题
（编号列出，含严重级别：阻断 / 一般 / 轻微）

## 遗留与建议
（转交下一步的事项）
```

## 5. ③ 用户确认要点（面向编程小白）

验收子代理通过后，向用户交付一段「亲手验证指引」：怎么启动、点什么、输入什么、预期看到什么。用户回复确认后才 commit+tag。用户有权以体验理由打回（如 UI 不像、手感不对），此时按 fix 流程处理。

## 6. 纪律

- 未走完流程的功能不得进入下一里程碑（防止债务滚雪球）。
- 二次验收报告原文入库，不允许事后美化。
- 阻断级问题必须当场修复；一般问题可挂 roadmap「技术债」区，但同一问题最多存活两个里程碑。
