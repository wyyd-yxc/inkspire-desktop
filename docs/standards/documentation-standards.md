# 文档撰写规范（Documentation Standards）

> 本规范是本项目所有文档的撰写依据。**先有规范，后有文档；先有文档，后有代码。**
> 版本：v1.0 · 制定日期：2026-08-22 · 任何修改需在文末变更记录中登记。

## 1. 文档目录总览

| 路径 | 用途 | 维护频率 |
|---|---|---|
| `docs/standards/` | 各类规范（文档/代码/git/验收） | 低频，修改需谨慎 |
| `docs/design/design-goals.md` | 设计目标：产品做什么、不做什么 | 里程碑级更新 |
| `docs/design/architecture.md` | 技术架构：模块划分、数据模型、AI 接口设计 | 架构变更时更新 |
| `docs/plan/roadmap.md` | 工作计划：里程碑看板，含状态 | 每完成一项更新状态 |
| `docs/worklog/worklog.md` | 工作日志：每次开发会话的记录 | **每次会话必须追加** |
| `docs/acceptance/` | 验收报告：每个功能一份 | 每次验收生成 |

## 2. 通用撰写规则

1. **语言**：一律使用简体中文；代码、命令、字段名保留英文原文。
2. **命名**：验收报告文件名格式 `YYYY-MM-DD-M<里程碑>-<功能slug>.md`，如 `2026-08-22-M1-bookshelf.md`。
3. **时效标记**：每份文档顶部标注「版本 / 日期」；正文涉及"当前状态"的表述必须与 roadmap 状态一致。
4. **可追溯**：描述一个决定时，写明「为什么」而不只是「是什么」。将来读者（可能是另一个 AI 模型）需要靠它理解上下文。
5. **禁止事项**：文档中不得出现任何真实 API Key、密码、私人信息。
6. **表格优先**：枚举型信息（列表、状态、参数）用表格；叙述性内容用段落。
7. **超链接**：引用外部资料给出完整 URL；引用仓库内文件用相对路径。

## 3. 工作日志（worklog）格式规范

`docs/worklog/worklog.md` 是模型交接的**第一入口**。每次开发会话**结束时必须追加**一节，格式如下：

```markdown
## [YYYY-MM-DD HH:MM] 会话 N：本次会话主题

- **使用的模型**：（模型名，便于排查风格差异）
- **完成内容**：（条目化，一两句一条）
- **修改的文件**：（关键文件列表，注明新增/修改/删除）
- **遇到的问题与解决**：（踩坑记录，供后来者避坑）
- **遗留问题**：（未完成、待确认的事项，没有写"无"）
- **下一步**：（下次会话应做什么，与 roadmap 对应）
```

规则：
- 只追加，不删改历史记录（写错了就在新条目里更正说明）。
- 新会话开工前：**先读 worklog 最新一节 + roadmap**，再动手。
- 会话中断（意外断电/上下文丢失）时，由下次会话的开头补记上次断点。
